# 咖啡角、看世界与回忆录实施计划

日期：2026-10-03
状态：方案已确认，页面改造已实施；真实照片与游记内容待补充。
目标：把三个栏目做成一本持续更新的个人生活杂志，保留计划李的辨识度，让真实内容、照片和个人体验成为视觉中心。

## 1. 品质目标与范围

以 Awwwards、Webby Awards、FWA 获奖级网站为设计品质参照，从排版、留白、视觉层级、色彩、动效、微交互、响应式和原创性八个维度持续检查与优化。此目标用于约束设计与验收，不代表获得奖项或评分认证。

本轮覆盖咖啡角、看世界、回忆录三个入口及其相关详情页，包括咖啡器具、豆子、探店、冲煮记录、澳大利亚旅行专题、景点、住宿和航班详情。首页、文章与认知工具仅在导航、内容关联和共享动效兼容确有需要时调整。归档、备份、测试页面不参与重设计。

保留已发布 URL、现有真实内容、Notion 同步能力和静态站点部署方式。设计修改落在模板、样式和生成流程中，不把生成后的 HTML 当作长期维护源文件。独立详情页先确认来源，再建立可重复生成的模板。

## 2. 当前问题与改造原则

| 栏目 | 当前问题 | 改造重点 |
| --- | --- | --- |
| 咖啡角 | 标题和统计占据首屏；器具型号、星级和参数比个人体验突出；内容分散在四个分类中 | 真实咖啡场景、近期冲煮、个人使用感受，以及豆子与器具之间的关联 |
| 看世界 | 航班信息靠前；目的地缺少视觉主角；历史日期仍以行程计划呈现 | 旅行封面、路线、章节与精选地点；明确计划和实际记录的区别 |
| 回忆录 | 导航与页面名称不一致；上传、管理和零数量统计突出；当前预览没有照片 | 以故事组织影像，优先服务读者；作者操作单独呈现 |
| 共享动效 | 所有页面重复幕布、不同类型卡片使用相近反馈，可能干扰连续阅读 | 统一节奏，按内容区分力度；只在明确可交互的位置提供动作反馈 |

首屏必须有明确主角和下一步阅读入口。统计退为辅助信息，不用空白占位、虚构评分、虚构体验或无内容卡片撑版面。

## 3. 统一视觉与交互方向

延续米白、黑色、橙色、直角、细线和局部硬阴影。标题、正文、元信息形成清晰层级；标题使用有辨识度的中文黑体，叙事正文适度搭配宋体，日期与配方采用等宽数字。字体优先复用现有资源，如需新增字体，先确认授权与加载体积。

| 栏目 | 辅助色与气质 | 主要视觉内容 | 交互特点 |
| --- | --- | --- | --- |
| 咖啡角 | 奶油白、浓咖啡色、少量器具绿 | 咖啡台、器具、豆子与杯中成品 | 器具轻微抬起，配方按需展开 |
| 看世界 | 米白、深蓝，少量橙色定位 | 目的地照片与路线 | 路线节点预览、章节定位 |
| 回忆录 | 温暖纸色、低干扰文字与边线 | 精选照片、短文字、相册封面 | 图片轻微放大，大图平滑切换 |

布局采用移动端优先。桌面用不对称编排与大小对比，手机按阅读顺序排成单列；每个栏目沿用同一套间距尺度和导航规则。图片保留适合内容的比例，封面裁切需指定焦点，大图查看保留完整画面。

动效保留用户喜欢的开篇入场和悬停反馈。建议会话首次访问播放完整品牌幕布，后续页面采用更短的标题入场；具体时长以实际浏览结果调整。阅读正文、已经展开的长内容和非交互装饰不持续倾斜。避免同一卡片外层与内层同时发生位移。触屏不依赖悬停，键盘焦点清晰；开启“减少动态效果”后内容仍完整可用。

## 4. 咖啡角实施内容

建议页面顺序：家庭咖啡馆封面 → 最近一杯 → 器具 → 豆子 → 探店与日记 → 关联阅读。

- 封面优先使用真实咖啡台照片，配简短个人介绍和浏览入口。没有合适照片时，使用已有器具素材做克制的编辑式构图，不生成或冒充用户家中的场景。
- 从已发布冲煮记录选择最近一条，显示豆子、器具、日期、配方和原有感受。仅在记录存在关联时提供跳转，不根据名称相似擅自建立事实关系。
- 主力咖啡机使用较大的展示区域，其他器具采用紧凑列表或两列编排。第一层展示名称、用途和已有使用感受；参数与详细说明放入详情层。展开、收起和阅读全文入口在手机上始终可发现。
- 豆子档案统一产地、烘焙度、处理法、风味词和品鉴笔记的顺序。回购意愿、推荐冲法等字段仅在有真实记录时呈现。
- 探店采用场所照片、地点和个人记录；日记按时间呈现，提供到相关豆子与器具的链接。保留原有分类访问方式，并支持链接直达分类或指定内容。
- 数量统计缩成一行，随真实数据生成。某类内容不足时使用紧凑布局。

完成条件：现有四类咖啡内容均可访问，展开和详情链接在桌面、触屏、键盘操作下有效；同步后数量、关联和版式不丢失。

## 5. 看世界实施内容

建议入口页顺序：旅行专题封面 → 简短引言 → 路线概览 → 精选地点 → 历次专题 → 影像入口。

- 澳大利亚专题作为现有内容最完整的样板。选取来源清楚的场景图作为封面，清楚区分用户实拍与目的地介绍图。
- 用轻量 SVG 绘制路线，优先避免引入地图 SDK。桌面节点可通过悬停或键盘聚焦显示预览，并可点击进入详情；手机使用纵向路线和直接可见的摘要。示意路线不冒充精确导航地图。
- 旅行专题按日期或地点形成章节，每个章节优先展示主题、场景和主要安排。交通、酒店、时刻、舱位等实用信息放在章节内的次级区域。
- 景点、酒店、航班详情统一封面、摘要、信息区、返回专题和相邻内容入口。长行程提供章节索引，并处理固定导航遮挡问题。
- 为旅行内容明确状态：计划、已完成、待补充回顾。日期已过只说明计划属于过去，不自动判定实际成行；现有三月内容在没有实际记录前标为历史行程计划。
- 旅行统计区分计划数量与已完成数量，缺少实际数据时不展示完成统计。移除无实际内容的“大型下一站”占位卡。
- 仅在存在对应内容时关联咖啡探店、文章和相册。

完成条件：读者能从目的地进入路线、找到某天安排、进入详情并返回；原链接保持有效，计划信息不被改写为未经确认的亲身经历。

## 6. 回忆录实施内容

建议页面顺序：精选故事封面 → 近期影像故事 → 按年份或主题浏览 → 完整相册。

- 将访客页面名称统一为“回忆录”，内容范围允许旅行和日常。每组相册包含封面、标题、时间范围、一段真实说明和排序后的照片。
- 相册采用人工选择的精选顺序，以大图、并置图片、竖图和短文字形成阅读节奏。照片较少时使用简单布局，避免为凑版面重复图片。
- 大图查看支持上一张、下一张、关闭、方向键、Esc 与焦点恢复；手机按钮足够易点，必要时增加左右滑动。标题、位置和说明不遮挡照片主体。
- 上传与管理进入独立作者入口，访客页不突出操作按钮。隐藏入口不等于权限控制，写操作仍依赖已有服务端认证与授权。
- 当前脚本先请求 `/api/gallery/list`，失败后读取 `gallery/gallery-data.json`。实施前确认生产环境是否提供这些 API；静态浏览必须独立可用，服务不可用不能被错误描述为“没有照片”。
- 本轮以静态相册展示和现有后台兼容为范围，不默认新建上传后台。若现有服务可用，则回归上传、删除和权限行为；若不可用，使用受控的本地素材整理与静态构建流程，不留下无效上传入口。
- 空相册不突出零统计，显示简洁整理说明。真实照片到位前，可以完成页面与数据结构，但不能把影像内容的最终验收标为完成。

完成条件：有照片、空内容、加载失败三种状态明确；相册排序、图片说明和大图操作正确；公开浏览不依赖作者登录。

## 7. 素材与数据准备

| 素材 | 用途 | 缺少时的处理 |
| --- | --- | --- |
| 咖啡台或日常冲煮实拍 | 咖啡首屏与最近一杯 | 先用现有器具素材完成构图，记录后续替换位置 |
| 已有冲煮笔记、豆子与器具关系 | 内容关联 | 只迁移能确认的关系，缺失字段不展示 |
| 旅行照片、实际行程与文字记录 | 专题封面、章节、状态 | 保留历史计划身份，介绍图明确来源 |
| 一组有标题、说明和顺序的真实照片 | 回忆录首个完整样板 | 完成结构与空状态，保留素材待办 |

允许使用 ChatGPT 图片生成能力，为三个栏目生成适合版式的封面插画、氛围配图、背景纹理、概念场景和辅助视觉素材，以改善展示效果。可根据已有器具或场景参考图生成配图，并统一构图、色彩和图片比例。生成图片可以作为正式设计素材使用；涉及个人经历、家庭环境、旅行现场或产品细节时，应明确其为 AI 生成示意，不冒充实拍或据此补写真实经历。回忆录中的纪实照片仍使用真实素材，生成图片可用于章节封面和辅助插画。

实施时先盘点项目已有文件、Notion 同步缓存和相册数据，再列出真正缺少的素材，不重复索要已有内容。新增图片记录来源、用途、替代文本、尺寸与裁切焦点；AI 生成素材另记录生成说明与参考素材来源；清理无需公开的定位元数据。封面与缩略图生成适当尺寸，保留原片用于大图。

## 8. 工程实施方式

- 主要入口：`templates/coffee.html`、`templates/travel.html`、`templates/gallery.html`。
- 栏目样式：`styles/coffee.css`、`styles/travel.css`、`styles/gallery.css`；公共尺度在共享样式中定义，栏目样式不覆盖其他页面。
- 栏目交互：`scripts/coffee.js`、`scripts/travel.js`、`scripts/gallery.js`；共享动效调整位于 `scripts/motion.js` 与 `styles/motion.css`。
- 生成与同步：`site_builder.py`、`sync_notion.py`。先明确咖啡局部生成页面与主页面之间的数据依赖，保留原有区域标记与同步契约；确需迁移时在迁移前后比对记录数量、正文和 URL。
- 独立详情页先建立来源清单，再抽取共享布局；不对所有 HTML 进行无差别内容替换。
- 跨栏目关联使用稳定 ID 或现有 URL，新增字段保持可选，历史记录缺少字段时正常降级。
- 开始前记录当前工作区和页面基线。当前尚未提交的成果属于已有工作，不能作为可丢弃文件处理。

| P3 旅行专题 | 完成入口、路线、章节、相关详情与状态呈现 | 路线和详情路径可用，历史内容身份准确 |

每完成一个阶段就构建并检查对应路径。遇到素材等待，继续完成不依赖素材的结构、交互与测试。上线、推送和部署属于后续发布动作，本计划交付以本地可审阅版本为准。

## 10. 验收标准

### 视觉与内容

| 维度 | 检查标准 |
| --- | --- |
| 排版 | 标题、正文、元信息层级清晰；中文断行自然；长标题与长地点名不溢出 |
| 留白 | 首屏有明确主角；段落与章节间距有节奏；不以大块空白掩盖内容不足 |
| 视觉层级 | 照片和个人记录优先，统计和操作次之；主要入口可直接发现 |
| 色彩 | 三个栏目各有气质，仍属于同一网站；文字与交互状态对比满足 WCAG AA |
| 动效 | 连续浏览不被反复遮挡；没有嵌套变形、抖动或明显布局跳变 |
| 微交互 | 悬停、聚焦、选中、展开、加载、失败状态完整；触屏能完成同样任务 |
| 响应式 | 检查 360、390、768、1024、1440 像素宽度；无横向溢出、遮挡或关键内容裁切 |
| 原创性 | 三个栏目有各自的内容组织方式；真实照片、记录与个人选择构成辨识度 |

### 功能与构建

- `npm run build` 成功；重复构建无重复资源注入与非预期内容变化。
- `python3 validate_site.py` 和 `python3 -m unittest discover -s tests -v` 通过；校验范围补充本轮迁移详情及相关资源，不能只依据现有 30 个页面校验宣称全站通过。
- 修改的 JavaScript 通过语法检查，浏览器无新增未处理异常；相册预期 API 降级单独记录。
- 走通咖啡分类、器具展开、相关记录跳转、路线预览、章节定位、详情返回、相册筛选与大图查看。
- 检查触屏、键盘、减少动态效果与图片加载失败场景。
- 以本地缓存或测试夹具验证内容同步不破坏布局；真实 Notion 同步只有在可用环境下实际执行后才标为通过。
- Lighthouse 在相同条件下检查三个入口和代表详情。以移动端性能至少 90 分、可访问性至少 95 分、LCP 不高于 2.5 秒、CLS 不高于 0.1 为目标，记录实测值及网络条件；实验室测试不替代线上真实用户数据。

### 优化与完成判定

每轮依次记录问题、修复、复测并更新截图。功能错误、内容失真、断链、溢出、焦点不可达和明显视觉缺陷必须修复；剩余素材缺项或服务限制单独列出。

最终进行一次完整浏览检查，直到八个维度中没有尚未处理的明确改进项。区分已经验证的结果、主观设计判断和待素材补齐项，不把“没有明显可提升之处”写成未经检查的保证。

## 11. 最终交付

交付三个栏目及相关详情的可运行页面、模板与同步改动、素材与来源清单、桌面和移动端截图、功能与性能验收记录，以及明确的待补充素材列表。验收记录保存到 `docs/qa/`，并更新页面来源清单。
